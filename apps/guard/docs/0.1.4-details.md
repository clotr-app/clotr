# Guard 0.1.4 in detail

## Copies of the example env file

- A one-line copy that renames the copy command first is stopped, like `function copy { gc $args[1] }; copy
  .env.example .env`, `Set-Alias copy gc; copy .env.example .env` or `alias cp=cat; cp .env.example .env`. 0.1.3 ran
  them and printed the real `.env`. After a function, filter, workflow or alias, or a write to PowerShell's function
  or alias drive, Guard reads a copy's last word as a file it may read.
- The same holds for `hash -p /usr/bin/cat cp`, for a `builtin`, `command`, `command -p` or `\` before `hash -p` or
  `alias`, and for a rename right after `if`, `elif`, `while`, `until`, `time`, `time -p` or a lone `!`.
  `if [ -f .env ]`, `while read`, `time npm ci`, `command -v cp`, `builtin cd`, `command cp` and `\cp` before a copy
  still run.
- Copying the example env file to the real one now runs in PowerShell with a second line or a comment after it, and
  on a cmd `if not exist .env` line with `^&` after the copy. A copy that reads `.env` or another secret file still
  stops, and so does any copy in a command that could make the copy another command first, as with a function or
  alias, in PowerShell or Bash. Bash still stops a copy with a comment or a second line after it, as 0.1.3 does.
- The cost of the rename check is that a command that sets up an alias or a function and copies the example env file
  is stopped, like `alias ll='ls -la'; cp .env.example .env`. So is one that only says alias, function or `hash -p`
  after a quote, a `(` or the words if, then, while or do, like `echo "alias ll='ls -la'" >> ~/.bashrc; cp
  .env.example .env`. 0.1.3 runs both.

## Reads of a secret file

- The shell check follows a `cd`, a variable, a rename or a link earlier in the same command, and reads what `xargs`,
  `find -exec`, `nice`, `timeout` and recursive copies like `rsync -a` hand on, so `cd .kube && cat config` stops.
- The shell check reads a variable inside a file's name as empty too, so `cat $u.env` and `type %u%.env` stop.
- The shell check reads PowerShell's Start-Process as running its program, so `Start-Process cmd '/c type .env'`
  stops, and inline code that opens a secret file with escaped quotes, pathlib, `os.path.join` or a variable stops
  too. The same text inside `echo` or `gh pr create --body` stops too, which is a false alarm.
- A file read through a tool server, like `get_file_contents` or `read_file` naming `.env`, is stopped by its name in
  Claude Code's and Cursor's tool hooks. Claude Code's also checks what's in the file for keys, as it did for the
  filesystem server's `read_file`. Cursor's only looks at the start of the file for a secret file's shape, like a
  service account key. A file that isn't on this computer, like one in a GitHub repo, is judged by its name.
- A file read under a WSL path, `\\wsl.localhost\` or `\\wsl$\`, is opened and checked for keys, where 0.1.3 let it
  through with a "couldn't check" note.
- A drive-relative path on another drive, like `type D:.env`, is judged below that drive's current folder when Guard
  can tell which it is, and by its name when it can't. A wildcard there, like `type D:*`, is matched at the top of
  the drive instead, which Guard lists once per check and only for part of its one-second limit. It stops where it
  matches a secret file, and also where that top lists too slowly, gives an error or holds more than 2,048 names. A
  search's pattern isn't a path, so `grep 'x:*' notes.txt` lists no drive and gets 0.1.3's answer, and so do the
  values of rg's `-g`, `--glob`, `--iglob` and `--type-add` and grep's `--include`. A share whose host is written in
  fullwidth letters is read as that host.

## Printing the environment

- The shell check stops more ways of printing the whole environment that 0.1.3 lets through, like `env > e.txt`,
  `(env)` and `sudo env`, and `printenv PATH` runs again.
- The shell check stops the environment printed through sudo, nice, ssh, a container or another language, like
  `docker exec app env` or `python3 -c "import os; print(os.environ)"`, and a key's variable read through sudo, nice
  or ssh, like `sudo printenv AWS_SECRET_ACCESS_KEY`.

## Fewer false alarms

- A git commit message that names a reader after a `;`, `(` or backtick, like `-m "read PORT once; type .env values as
  strings"`, runs. So does the same message written the way Claude Code writes commits, `-m "$(cat <<'EOF'` with the
  text on the lines below, since a quoted end word means the shell runs nothing in it. Any other `$( )` or backtick
  inside a double-quoted message still gets checked, and so does a here-document whose end word isn't quoted. If a
  line in the text starts with the end word and goes on, like `EOF)`, the whole command gets checked, since Bash can
  end the text at that line and run what follows.
- A wildcard that starts with a letter, like `cat config*` or `grep -n foo c*.json`, is looked up in its folder, so it
  runs where it matches no secret file and is stopped where it does.
- The shell check's folder walk stops fewer recursive searches of a big project. Two different readers of one folder
  each get the whole walk, and rg's walk leaves a git-ignored folder like `target/` as soon as it knows. Certifi's
  `cacert.pem` in a virtual env the search reads is let through, where 0.1.3 took it for a key. On Linux a folder of
  hundreds of thousands of files is stopped at the walk's time limit, sooner than before. Windows still lists it in
  one go first.

## Hooks that wait

- Hook input that never closes, a tool call nested over 1,000 deep and a network share that stalls on its first file
  get the time-out answer in time, where 0.1.3 could hang, run late or let the call through. So does a search given
  over 100,000 filters or 1 MiB of them.
- A Git that doesn't answer, on a network drive or behind a sign-in window, no longer holds up the hooks. Guard gives
  each Git call 2 seconds, says Git didn't answer, and the Git check stops that commit.
- On a busy computer where Git is slow to start, a content search in a Git project waits for Git up to 2 seconds in
  all, however many git-ignored secret files it finds, and is checked to the end if Git has answered by then. 0.1.3
  held it after 250 ms. A search whose check still runs out of time is held, as before, unless each of its Git calls
  answered within 250 ms. Then it goes through, as on 0.1.3.
- A read of a named pipe is judged by its name and never opened, so the hook answers at once. In Claude Code, 0.1.3
  waited on the pipe until something wrote to it, and now it says it couldn't check the read.

## Prompts and errors

- Sending a stopped prompt again lets it through only in the assistant session that showed the warning. In 0.1.3 a
  resend in another window, or in another assistant, counted too. A hook event with no session id still shares one
  record for that assistant.
- When Guard hits an error of its own, like a missing engine file, it stops the prompt instead of letting it through,
  and asks about or stops a read or an MCP tool call. 0.1.3 let all three through with a note.
- What Guard found and let through now shows in the assistant's window, not only on stderr.

## clotr-guard check

- With more than one file, it checks every file it's given, in order, and starts each finding with its file's name.
  `--json` still takes one file.
- A finding's masked form got shorter. It shows none of a password and at most a quarter of anything else, in
  `clotr-guard check`, the Git check and Clotr MCP, like `AK…3N` for a key where 0.1.3 showed `AKIA…3N`.
- It finds a key in a UTF-16 file without a byte order mark that it used to give up on, like a big-endian one, one
  mostly in Hindi or Japanese, one with a UTF-8 line added, or a UTF-8 log with UTF-16 lines in it. With no key
  found, such a file still gets "couldn't check". Guard also finds a key in either part of a UTF-16 file with a byte
  order mark and a UTF-8 line added to it, and lists one in a file with stray control bytes.

## Setup

- Guard's Windows hooks now run from a user folder or install path with a curly apostrophe, like `C:\Users\O’Brien`.
  A hook 0.1.3 already wrote there doesn't run until you run `clotr-guard setup` again, which replaces it. `remove`
  takes it away too.
- Setup works again after a remove on a settings file that changed in between. It keeps the earlier backup and says
  where it is, and an empty settings file or a `hooks` entry Guard can't read now gets its own message.

## Speed

- Each hook call starts a little faster than it would otherwise. After its first check, Guard saves the engine's
  compiled code in its own data folder and loads it from there next time. It uses that file only if only you can
  write to it (on Windows, only inside your user folder) and it was made by the same Node from the same engine.
  Otherwise Guard loads the engine the way it always has. When you set its data folder yourself with
  `CLOTR_GUARD_DATA_DIR`, or set `XDG_STATE_HOME` to a relative path, it always loads that way and saves no code.
- Even so, each hook call takes longer than in 0.1.3, mostly from loading Guard's own code, which is now in 56
  files, and the engine's bigger readable bundle. Each hook loads only the files it uses. The shell hook loads 14 in
  its own process and 41 in its check's, the read hook 30 and `clotr-guard check` 16, where 0.1.3 loads 4.

## The engine

- The engine is 1.6.4, up from 1.6.1 in 0.1.3, so Guard gets what engine 1.6.2, 1.6.3 and 1.6.4 changed. A password
  in a link with a login, like `smb://sam:hunter2!@nas.example.org/share`, is found as a connection string, where
  0.1.3 found nothing. The engine's changelog in
  `apps/engine/CHANGELOG.md` and its details docs say the rest.
