# Guard 0.1.2 in detail

- The shell check fails closed. When it hits an internal error or its 10-second deadline, the command is stopped and
  the message says which, and a hook that crashes once it has started stops it as a check that didn't finish. Prompt,
  file-read and MCP tool checks still let the action through with a visible note when they hit an internal error.
- Prompt, file-read and MCP tool checks have the same 10-second deadline, inside the 15-second hook timeout Guard
  sets. A check that runs out of time no longer lets the action through: a prompt is stopped, even when sent again,
  and a read or tool call is put to you (or stopped where the assistant can't ask). The message says part of it wasn't
  checked. A text of 64K characters or more is checked in a worker thread, so the deadline holds for it too.
- `rg <pattern> <folder>` on a git-ignored folder is stopped whether or not ripgrep is installed.
- A process's environment under `/proc` is stopped when the path to it is written out from the root, with `*`, `?`
  or `[…]` globs (`/p*/self/env*`), `$$`, a task's folder, `..`, extra slashes or `/dev/fd/..`. A glob as `cp`'s last word is
  checked as files it copies too, since the shell can expand it to several paths and cp copies all but the last. It's
  taken as only where cp copies to when the command is that one `cp` call and Guard lists one path or none for a plain
  `*` glob in the working folder or one under it.
- A broad glob like `src/*` is stopped only when it can match a secret file in its folder, and `[...]` classes are
  read the way the shell reads them. A glob with many stars, or a megabyte of paths in one command, is checked well
  inside the hook's timeout.
- `findstr`'s joined switches and rg's long unrestricted flag are read, and a Windows short name for a secret file
  (`ENV~1`) is caught like the long name, also behind a `\\?\C:\` or `\\.\C:\` device path.
- A shell command that names more paths than the check can look up in time is stopped when a path past that point is
  on disk, instead of being judged by its name, so padding a command no longer slips a link or a short name through.
- `grep -r`, `rg`, `cp -r`, `diff -r` and `findstr /s` now have the folders they read checked in full, up to 131,072 entries in all,
  within the shell check's first 5 seconds. A folder too big or too slow for that stops the command, and the message says so.
- A path with a long run of dots, spaces or colons in it, a long quoted run of blank space, or a glob at the end of a
  very long path, is read in linear time. It used to hold the shell check past the hook's timeout, so the command went
  ahead unchecked.
- Paths on other computers (`\\host\share`, `//host/share`, `\\?\`, `\\.\` and `\??\` paths that don't name this
  computer's drive, `file:` URLs and `/net/<host>/...`) are judged by name alone. Guard never looks them up, lists
  them, or runs Git or ripgrep in them, since on Windows looking one up connects to that host, which can hand it your
  sign-in hash. A device path to a file on a drive (`\\?\C:\proj\.env`) is checked for a secret file as the drive path
  it opens, and a part of a path on another computer that could be a short name stops the action. WSL paths
  (`\\wsl$\...`, `\\wsl.localhost\...`) count as network paths too, so a file there is judged by its name and its
  contents aren't checked. A search, a recursive reader or a file read through a device path to a drive reads the
  drive's folder, so a git-ignored secret file in it is caught and a read's contents are checked. A drive-relative path
  (`C:Users\me\...`, or `C:` alone) named from a folder on another computer is stopped, since Guard can't tell which
  folder it opens, and so is a recursive read or search of a credentials folder there (`.kube`, `.ssh`, `.aws`), also
  as the working folder, through `..`, by a glob or by a filter (`.kube/*`). A search's filter there that singles out
  a secret file by its name (`--glob=.env`, `**/id_e*`, `proj/.env*`, `*e/config`) or a credentials folder above it
  (`.ssh/id_e*`, `?ssh/*`) is stopped, and so is a file type rg is given such globs for (`--type-add 'k:.env*' -tk`).
- A drive's share on this computer (`\\localhost\C$\...`, `\\127.0.0.1\c$\...`, `\\?\UNC\localhost\C$\...`), or the
  drive's own volume by any of the system's names for it (`\\?\Volume{...}\...`, `\\.\HarddiskVolume3\...`), is
  checked as the drive path it opens, so a link or a short name behind it is caught and a read's contents are checked
  (a named stream's, for `notes.txt:hidden`), also with a `.` or `..` that stays below the share or volume, or with its
  backslashes doubled, as in a script's string. A device path through any other name in the system's namespace
  (`\\.\STORAGE#Volume#...`, a DOS device a program defined, or a port or disk name with a path below it, like
  `\\.\COM97\...`, a root ending in a dot or a space the system keeps, like `\\?\C:.\` or `\\.\C: \`, or a root with a
  stream name, like `\\.\HarddiskVolume3:x\...`) could open any file, so it's stopped, without looking it up. A drive's
  share on another computer is judged by the drive path's name, still without looking it up.
- A Windows path with a part ending in a dot, a space or a stream name (`kubelink.\config`, `ENV~1.`) is checked as the
  file Windows opens, so a link or a short name written that way is caught, also in a search or a recursive reader. A
  shell command padded with so many of these, or of share paths, that checking them takes over a second is stopped,
  so the check still answers in time.
- A file read's path checks keep the 10-second deadline, so a slow disk puts the read to you (or stops it where the
  assistant can't ask) instead of holding the hook. A path too long for the system to open is judged by its name. A
  read whose path opens one file as written and another as Windows tidies it (`keys.txt.`, `a:hidden.`) checks both,
  so a file planted under the other name can't stand in for the one read, and a note either one has is kept.
- A search or a recursive reader judges each file by its whole path too, so searching `.kube` itself, or a link to
  it, is stopped for `config` there.
- A search glob that matches a git-ignored or hidden secret file is stopped, since ripgrep's `--glob` overrides its
  ignore rules, and one with a leading slash (`/.e*`) is read from the folder searched, as ripgrep reads it. A
  git-ignored file no longer ends Gemini CLI's `read_many_files` check before the files after it. Claude Code's Grep
  glob is read as the list of globs it is (`*.md,.env`), and `findstr`'s quoted `/d:` folder list without its quotes.
  A search whose globs can't all be checked by the 10-second deadline is held as a check that didn't finish, and so is
  one that finds a secret file whose ignore check doesn't answer in time.
- A search glob is also read with its backslash escapes (`.e\nv` is `.env`), one with more braces than Guard expands
  counts as matching every file, and a value quoted after an option's `=` (`rg --glob='.env*'`, `grep
  --include=".env"`) is read without its quotes.
- GNU grep's shortened long options and values (`--rec`, `--inc=.env`, `-d rec`) are read as grep reads them, and
  `is_secret_file` judges a path with a trailing separator (`.kube\config\`, `.kube\config\ `) as the file.
- A filesystem MCP server's file reads (`read_text_file`, `read_media_file`, `read_multiple_files`) are checked as
  reads of the files they name, also in Claude Code's MCP tool hook, which before checked only their arguments.
- A shell path under the home folder (`~/...`, `$HOME`, `$env:USERPROFILE`, `%USERPROFILE%`), or in Claude Code's Bash
  tool a Git Bash drive path (`/c/Users/...`, `/tmp`), is checked as the path the shell opens, so a link or junction
  there is caught, and a recursive reader's credentials folder named through a variable Guard can't read
  (`grep -r x $SOMEWHERE/.kube`) is stopped by its name.
- A PowerShell list of paths (`gc notes.txt,.env`) has each path checked, and a word's quoted parts are also read
  joined, as the shell joins them (`cat "$HOME"/kj/config`, `cat '.'env`).
- A shell command is also read with the escapes and quoting of each shell that could run it: Bash's backslash,
  `$'...'` and `$"..."`, PowerShell's backtick and cmd's caret (`cat .e\nv`, `` gc `.env ``, `cmd /c type .e^nv`). In
  PowerShell a parameter's value after a colon (`gc -Path:.env`) and a path after a provider name (`FileSystem::C:\...`)
  are read, and an input redirection's target is read whole, its quoted parts joined (`< "$HOME"/kj/config`).
- That reading is also done with the shell's comments read, no quotes or escapes read in them, and a here-doc's or
  here-string's body skipped, its delimiter read as Bash reads it (`<<E\OF`), as well as without, never instead. It is
  also read with quotes ended at line breaks, and with an escaped line break in a quote or a comment ending the line,
  takes PowerShell's curly quotes and dashes for plain ones (`gc ‘.env’`) and reads carets inside `cmd /c "..."`.
  Quotes inside a double quote's command or variable pair as the shell pairs them (`"$(echo "'")"`), also one inside
  another, which ends where Bash ends it (`"${x:-{}"`, not at a `case` pattern's `)`). A Bash backtick's command is read
  on its own, whatever quotes are in it, and PowerShell's `${...}` as a name. A command PowerShell can't parse (a `<`
  starting a word outside a string and not after `--%`, as in a Bash here-doc) isn't read with its escapes, nor is a
  comment's text or a multi-line here-string's. A command's name is read without its quotes (`'cat' .env`,
  `& 'gc' .env`), a variable inside a word as empty (`.e${X}nv`) and a Bash variable's default in its place
  (`.e${X:-n}v`), a read-write redirection (`<>.env`) as a read, and `~+`, `~0` and `/proc/self/cwd` as the working
  folder.
- Each command is also split where its shell splits it. A `|`, `;`, `&`, `)` or backtick inside quotes no longer
  ends the list of files a command reads, so `cat "a|b" .env`, `Get-Content "a;b", .env` and `type "a&b" .env` are
  stopped in Bash, PowerShell and cmd. A PowerShell list that goes on past a line break after a comma, the words
  after `--%`, a `(…)` or `@(…)` given as an argument, `cmd /c` glued to its command or to switches before it or
  written `//c` in Git Bash, a Bash function's body, and a wrapper word written in quotes (`"sudo" cat`) are read
  too, and PowerShell's `cp` and `copy` are read as Copy-Item, with its parameters and lists. Every command is still
  also checked the way earlier versions checked it, and either check can stop it, so nothing they stopped goes
  through, except where all that stopped it was the bare `*` the fix that follows drops. That
  keeps their false alarms on a quoted `|` in a search (`grep -rn 'a|b' src` when the folder holds a secret file) and
  on a PowerShell reader followed by a line break or a comment that names one. One is fixed where Guard can tell what
  Bash will read: when Claude's Bash command starts with a call of `cat`, `head`, `tail`, `tac`, `nl`, `od`,
  `paste`, `fold`, `cut`, `uniq`, `base64` or `cp`, such as `cat "READ ME"*`, that ends at `;`, `&&`, `||`, a line
  break or the command's end, with no `|`, `&`, `<`, `>`, parenthesis, brace, `$`, backtick or `\` in it, even
  quoted, and Guard lists exactly one file with no other name, or one folder, starting with that name in the working
  folder or one under it, it's checked in place of the bare `*`, and the quoted name still is too. Where Guard can't look up every
  path in the command on disk, it keeps the earlier reading.
- A Git Bash path is read as Git Bash tidies it (`/./c/...`, `/tmp/../c/...`, `/proc/cygdrive/c/...`), a whole drive in
  Git Bash (`grep -r x /c`) is stopped by its name, and on Windows a recursive reader's credentials folder named through
  a path starting with one slash is stopped by its name in any shell.
- A read or search that names its path under more than one key (`path`, `file_path`, `dir_path` and the like) has each
  checked, also when another key holds a number or an object, and a `~/...` path is checked as the file under the
  home folder, also by `is_secret_file`. A big repository's rg listing past the read hook's buffer is answered from
  ripgrep's rules.
- Clotr MCP's tools each have a title and read-only annotations, and `initialize` sends short instructions on when to
  call each tool. When the engine runs out of time, `check_text` and `clean_text` return `truncated: true`, and
  `check_text`'s verdict says part of the text wasn't checked. `clean_text` hides values from the same scan it lists
  them from, and `is_secret_file` judges a path on another computer by name without looking it up.
- With personal details off, the default, every kind the engine groups as personal stays out of the checks, not only
  the ones a word list caught. Card numbers, card security codes, gift-card codes and bank account numbers stay checked
  like credentials.
- Double-quoted credentials in MCP tool arguments, such as `DB_PASSWORD="..."`, are caught.
- The commit check reads added lines that start with `++ ` and a path whose type changed. When the engine runs out of
  time on a file, it names the file and stops the commit. `clotr-guard check` returns 1 for a text it didn't check to
  the end.
- A key among a megabyte of email addresses is found in about two seconds instead of 30 or more, which used to pass
  the hook timeout and let the action go ahead unchecked.
- `clotr-guard check <file>` reads UTF-16 files, the way Windows PowerShell 5.1's `>` writes them.
- A dry-run Git remove only reports the change, so cancelling VS Code's preview leaves the commit check on.
- Guard and its engine load in VS Code 1.57's Node 14 extension host again.
- The engine is the one in Clotr 1.6.1, with its new detection, including Irish PPS and New Zealand IRD and NHI
  numbers.
